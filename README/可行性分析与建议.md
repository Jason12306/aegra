

# 从 NestJS 自研迁移到 Aegra 的可行性分析与建议

> 针对当前 NestJS LangGraph Server 实现存在的问题，评估引入 Aegra 作为 AI 服务层的必要性

---

## 概览

| 指标               | 数据                 |
| ------------------ | -------------------- |
| 当前缺失生产级功能 | 8+ 项                |
| Aegra 开发周期     | 0（开箱即用）        |
| 自研预计工期       | 4–8 周（仅核心功能） |
| 许可证             | Apache 2.0，商用免费 |

---

## 一、当前问题 vs 引入 Aegra 后

### 当前：NestJS 自研

- ❌ 无分层：业务逻辑与 AI 执行耦合
- ❌ 数据结构难以对齐 Agent Protocol
- ❌ 无任务队列，重启任务全部丢失
- ❌ 无崩溃恢复机制
- ❌ 无流式跨实例支持
- ❌ 无持久化 checkpoint
- ⚠️ 持续投入开发资源维护

### 引入后：NestJS + Aegra（推荐）

- ✅ NestJS 专注业务层，分层清晰
- ✅ 完整实现 Agent Protocol（Assistants / Threads / Runs）
- ✅ Redis 任务队列 + 崩溃恢复
- ✅ 租约机制保障 Run 不丢失
- ✅ SSE Pub/Sub 支持多实例扩容
- ✅ PostgreSQL checkpoint 持久化
- ✅ 团队聚焦 Agent 业务逻辑开发

## 二、功能对比详情

| 功能维度          | NestJS 自研现状                               | Aegra                                                         |
| ----------------- | --------------------------------------------- | ------------------------------------------------------------- |
| 架构分层          | ❌ 未分层，业务逻辑与 AI 执行耦合             | ✅ NestJS 业务层 + Aegra AI 层，职责清晰                      |
| 数据结构          | ❌ 自定义，与 LangGraph SDK 不兼容，对接困难  | ✅ 完整实现 Agent Protocol（Assistants / Threads / Runs）     |
| 状态持久化        | ❌ 缺失或自实现，无标准 checkpoint 机制       | ✅ PostgreSQL + AsyncPostgresSaver，自动注入每个图            |
| 任务队列          | ❌ 请求生命周期内同步执行，断线即中断         | ✅ Redis 队列，Run 异步分发，与 HTTP 生命周期解耦             |
| 崩溃恢复          | ❌ 无，服务重启或 Worker 崩溃任务永久丢失     | ✅ 租约机制：心跳续约 + Reaper 自动重新分配崩溃任务           |
| 流式输出          | ⚠️ 基础实现，仅支持单实例，无跨实例推送       | ✅ 8 种流模式，Redis Pub/Sub 支持多实例，断线自动重连+回放    |
| 认证授权          | ⚠️ 仅业务层，AI 层无独立认证                  | ✅ 插件化认证：JWT / OAuth / Firebase / 自定义 Python Handler |
| 横向扩容          | ❌ 困难，无队列和共享状态，多实例会冲突       | ✅ 多 Worker × 多实例，Redis 协调，线性扩容                   |
| 可观测性          | ❌ 缺失，无 Agent 级别的链路追踪              | ✅ OpenTelemetry，支持 Langfuse / Phoenix / 任意 OTLP 后端    |
| Human-in-the-Loop | ❌ 需自研，暂停/审批机制实现复杂              | ✅ 内置 interrupt，支持审批关卡，状态可恢复                   |
| 向量存储          | ❌ 需额外集成，无内置语义搜索                 | ✅ pgvector 内置，支持 OpenAI embedding                       |
| 开发语言          | ⚠️ TypeScript，LangGraph 生态主要在 Python 端 | ✅ Python，与 LangGraph 生态完全对齐，功能最全                |

## 三、NestJS 自研当前缺失功能清单

- ❌ 任务队列（Redis Job Queue）
- ❌ 租约式崩溃恢复（Lease Recovery）
- ❌ PostgreSQL Checkpoint 持久化
- ❌ 跨实例 SSE Pub/Sub
- ❌ 标准 Agent Protocol 数据模型
- ❌ Human-in-the-Loop 支持
- ❌ OpenTelemetry 链路追踪
- ❌ pgvector 语义存储
- ❌ Graph Factory 动态图构建
- ❌ Cron 定时任务调度

## 四、引入 Aegra 的注意事项

### ⚠️ 版本处于 0.x 阶段

当前最新版本 `0.9.18`，minor 版本升级可能包含破坏性变更（endpoint 重命名、schema 迁移）。建议锁定版本，升级前仔细阅读 Changelog。

### ⚠️ 核心贡献者较少（< 10 人）

遇到边缘 Bug 可能需要自行 fork 修复。建议团队具备基础 Python/FastAPI 能力，能够阅读和修改源码。

### 🟢 需要 Python 运行环境

新增 Python 技术栈，团队需要有 Python 开发能力。Aegra 负责 AI 层，NestJS 继续负责业务层，两者通过 HTTP 接口通信，互不干扰。

### 🟢 需要维护两套服务

NestJS + Aegra 双服务部署，运维复杂度略有提升。但这也是「业务层/AI层」分离的代价，与微服务架构思路一致，长期收益大于短期成本。

### 🟢 Thread 归属需在 NestJS 中管理

Aegra 本身不做业务级的用户隔离（`noop` 模式），需要在 NestJS 数据库中维护 `user_id → thread_id` 的映射，并在每次操作前校验归属权。

## 五、推荐架构

```
┌─────────────────────────────────────────────────────┐
│                    客户端（Web/App）                  │
└──────────────┬──────────────────────────────────────┘
    AI 对话请求 │ 业务请求              
               ▼                      
┌──────────────────────┐  ┌───────────────────────────┐
│     NestJS（业务层）   │  │      Aegra（AI 服务层）    │
│                      │  │                           │
│  - 用户注册/登录       │ 转│  - Agent 执行             │
│  - JWT 认证           │─→│  - Thread 管理            │
│  - 会话关联           │ 发│  - 流式输出（SSE）         │
│  - 权限管理           │  │  - 状态持久化             │
│  - 业务数据 CRUD      │  │  - 工具调用 / MCP         │
└──────────┬───────────┘  └──────────┬────────────────┘
           │                         │
           ▼                         ▼
┌──────────────────┐      ┌──────────────────────────┐
│    业务数据库      │      │  AI 数据库（PostgreSQL）  │
│ (MySQL/PostgreSQL)│      │  + Redis（队列 / Pub/Sub）│
└──────────────────┘      └──────────────────────────┘
```

两者通过 `thread_id` 作为纽带关联：NestJS 负责「谁能访问什么」，Aegra 负责「AI 怎么执行」。

## 六、结论

当前 NestJS 自研方向存在根本性的架构问题：在错误的语言生态中重新实现一个已有成熟方案的基础设施层，不仅开发周期长（预计 4–8 周仅完成核心功能），且长期维护成本高，与 LangGraph Python 生态存在持续的功能差距。

引入 Aegra 后，NestJS 回归本职（用户、权限、会话关联等业务逻辑），Aegra 承接所有 AI 执行层能力。两者职责边界清晰，团队可以将精力集中在 Agent 业务逻辑本身，而不是基础设施的重复建设。

**综合功能完整度、开发效率和长期维护成本，建议采用 NestJS（业务层）+ Aegra（AI 层）的双层架构，尽快完成迁移，终止当前自研 LangGraph Server 的持续投入。**
