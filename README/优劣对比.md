基于我们整个对话中对 Aegra 架构、LangGraph 运行机制的深入分析，从多个维度详细列举：

---

## 一、数据结构层面

**没有标准数据模型**

LangGraph 生态基于 Agent Protocol 定义了一套标准实体：Assistants、Threads、Runs、Checkpoints。NestJS 需要从零设计这套数据结构，稍有偏差就会导致与 LangGraph SDK 不兼容，客户端调用时需要大量适配层。

**Checkpoint 结构极其复杂**

LangGraph 的 checkpoint 不是简单的 JSON 存储，它包含图的完整执行状态（channel values、pending writes、版本向量等），数据结构与 LangGraph 内部强耦合。TypeScript 侧几乎无法正确实现，官方的 `AsyncPostgresSaver` 是 Python 实现，直接复用才是正确路径。

**Run 状态机需要自实现**

一个 Run 有完整的生命周期：`pending → running → success / error / timeout / cancelled`，状态转换逻辑、并发保护、超时处理都需要自己实现，遗漏任何一个边界条件都会导致数据不一致。

---

## 二、任务执行层面

**同步执行与 HTTP 生命周期绑定**

NestJS 中 Agent 图的执行默认在请求上下文内进行，客户端断开连接（网络抖动、手机切后台、Nginx 超时）会直接中断图的执行。对于需要几十秒甚至几分钟的复杂 Agent，这几乎是必然发生的问题。

**没有任务队列，无法控制并发**

没有任务队列意味着没有背压机制。100 个并发请求会同时创建 100 个图执行任务，导致：

- 数据库连接池耗尽
- LLM API 触发并发限速（429 错误）
- 内存急剧上涨，服务雪崩

**服务重启导致任务全部丢失**

每次部署上线都会中断所有正在执行的 Agent，这些 Run 在数据库中永远停留在 `running` 状态，用户看到请求卡死，没有结果也没有错误。在频繁迭代的开发阶段尤为严重。

**没有崩溃恢复**

Worker 进程因 OOM、未捕获异常等原因崩溃时，正在执行的任务直接丢失，没有任何重试机制。用户必须手动重新发起请求，且无法感知失败原因。

---

## 三、流式输出层面

**SSE 无法跨实例**

单实例时 SSE 勉强可用，但一旦部署多个 NestJS 实例做负载均衡，客户端连接的实例与执行任务的实例可能不是同一个，进程间内存不共享，流式数据无法送达客户端。

**断线重连后数据丢失**

客户端 SSE 断线重连时，没有事件回放机制，断线期间产生的 chunk 全部丢失，用户只能看到不完整的输出。

**Nginx 缓冲问题难以排查**

SSE 经过反向代理时，如果没有正确配置 `proxy_buffering off`，流式输出会变成批量返回，表现为响应长时间没有内容然后一次性全部输出，用户体验极差且难以定位根因。

---

## 四、架构设计层面

**业务逻辑与 AI 执行高度耦合**

用户管理、权限校验、会话关联、Agent 执行混在同一个服务中，任何一层的变动都可能影响其他层。AI 层需要频繁迭代 Prompt、工具、图结构，与业务层耦合会大幅降低迭代速度。

**无法独立扩容 AI 层**

AI 推理是计算和 I/O 密集型任务，业务请求是轻量 CRUD 操作，两者的扩容需求完全不同。耦合在一起只能整体扩容，资源浪费严重。

**TypeScript 与 LangGraph Python 生态持续脱节**

LangGraph 的新特性（Graph Factory、ServerRuntime、新的流模式、MCP 集成等）首先在 Python 侧发布，TypeScript 侧往往滞后数个版本甚至永远不支持。用 NestJS 实现意味着永远在追赶一个不断扩展的 Python 生态。

---

## 五、可靠性层面

**无 Human-in-the-Loop 支持**

LangGraph 的 HITL 依赖 checkpoint 机制：图执行到 interrupt 点时暂停，将状态持久化，等待人工审批后从断点恢复。这套机制与 checkpoint、状态管理深度绑定，在 NestJS 侧从零实现极其复杂，容易出现状态不一致问题。

**无 Cron 定时任务**

Agent 的定时触发（如每天定时执行数据分析 Agent）需要额外引入调度库，并且面临多实例重复触发、任务堆积、失败重试等问题，需要完整的分布式调度实现。

**无租约保护**

多实例场景下，同一个任务可能被多个 Worker 重复执行（重复消费），没有租约机制无法防止这种情况，导致数据重复写入或 LLM 重复调用产生额外费用。

---

## 六、可观测性层面

**没有 Agent 级别的链路追踪**

普通的 HTTP 请求追踪无法覆盖 Agent 内部的执行细节：哪个节点耗时多少、哪次工具调用失败、LLM 输入输出是什么、Token 消耗多少。缺少这些数据，生产问题几乎无法定位。

**无结构化的 Run 历史**

每次 Agent 执行的完整过程（输入、输出、中间步骤、耗时、状态）需要自行设计存储方案，否则出现问题时无法回溯。

---

## 七、安全层面

**无 Thread 级别的访问控制**

没有标准的 Thread 归属模型，任何知道 `thread_id` 的请求都能读写该会话的状态，需要在每个接口手动实现归属校验，容易遗漏。

**AI 层缺乏独立认证**

业务层和 AI 执行层共用同一套认证，无法为 AI 层单独设置更细粒度的权限控制（如哪些用户能用哪些 Agent、哪些工具只有管理员能触发）。

---
